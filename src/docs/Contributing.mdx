# Contributing Guidelines

We welcome internal contributions from the FMDQ engineering team to extend and refine the Design System. This page covers how we build components here, the conventions are not optional, they are what keeps the library consistent and on-brand.

---

## Local setup

Working on the design system itself means running this repository locally. (If you only want to *use* the system in an app, see <a href="../?path=/docs/🏁-getting-started--docs" target="_top">Getting Started</a> instead — you don't need to clone anything.)

**Prerequisites:** Node.js v18+, npm or yarn, Git, and access to the FMDQ internal design system repository.

Clone the repository and install dependencies:

```bash
git clone https://github.com/fmdq/design-system.git
cd design-system
npm install
```

Then start the design system locally:

```bash
npm run storybook
```

Storybook will be available at `http://localhost:6006`.

## Workflow

1. **Raise an issue.** Before building a new component, raise an issue describing the missing functionality and its potential layout impact. **Confirm the Figma design exists first** and that the component is tracked in [`rules/FIGMA_STORYBOOK_MAPPING.md`](rules/FIGMA_STORYBOOK_MAPPING.md).
2. **Branch.** Branch off `main` using `feature/<component-name>` or `fix/<component-name>`.
3. **Extract the spec from Figma.** Never guess or invent values. Pull the full spec from Figma via the MCP tools (`figma_get_components`, `figma_get_node`), see the <a href="../?path=/docs/🖇️-mcp--docs" target="_top">MCP</a> page. The mandatory step-by-step is in [`rules/FIGMA_STORYBOOK_RULES.md`](rules/FIGMA_STORYBOOK_RULES.md).
4. **Build to convention** (see below).
5. **Check parity.** Run `figma_diff_tokens` / the design-parity check before marking a component complete, and update the mapping file with the status and date.
6. **Open a PR.** Request review from at least one core maintainer. Ensure your Storybook additions render correctly.

## Component structure

Each component lives in its own folder and ships four files:

```
ComponentName/
  ComponentName.tsx          # implementation
  ComponentName.css          # co-located vanilla CSS, imported in the .tsx
  ComponentName.stories.tsx  # one story per Figma variant
  ComponentName.docs.mdx     # Overview, Figma embed, variants, props table, usage
```

Place it under the correct tier:

◼ **`elements/`**; atomic primitives (Button, Input, Badge, Chip, Toggle…)

◼ **`components/`**; composites (Table, Tabs, Modal, Dropdown, Card…)

◼ **`layout/`**; full-page structure (AppLayout, TopBar, PageHeader)

Export every public component from [`src/index.ts`](src/index.ts).

## Coding standards

◼ **Design values come from tokens, always.** Use the CSS variables in `src/tokens.css` (`var(--color-primary-default)`, `var(--spacing-md)`, etc.). Never hardcode a colour, spacing, typography, or shadow value that is already tokenised. If a token is missing, add it rather than hardcoding.

◼ **CSS naming uses the `fmdqui-` prefix with BEM-like modifiers:** `fmdqui-button`, `fmdqui-button--primary`, `fmdqui-button--sm`.

◼ **Keep CSS in the co-located `.css` file**, imported from the `.tsx`. No inline style objects for anything that belongs in CSS.

◼ **Type components explicitly** with React `FC`.

◼ **Accessibility is required:** valid roles, `aria-label`s where needed, and sensible semantic structure.

◼ **Variant prop names mirror Figma property names exactly,** and every Figma variant has a matching Storybook story.

## Before you open a PR

Run the local checks:

```bash
npm run lint
npm run typecheck
npm run build
```

Then start Storybook (`npm run storybook`) and confirm your component renders, all variants appear, and the Controls panel works. Finally, run the <a href="../?path=/docs/✅-branding-todo--docs" target="_top">Brand & UI Quality Checklist</a> against anything user-facing.

---

## Documentation requirements

Every documented component needs a `.docs.mdx` with:

◼ Overview ◼ Figma embed ◼ All variants (with `sourceState="shown"`) ◼ Props table ◼ Usage guidelines

A component is not "done" until its docs page exists and `rules/FIGMA_STORYBOOK_MAPPING.md` records its status and last parity-check date.
